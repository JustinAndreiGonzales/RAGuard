# RAGuard

A permission-aware RAG (Retrieval-Augmented Generation) chatbot. Users upload documents, which are chunked and embedded into a vector store, and a chatbot answers questions grounded in that content — but retrieval only ever surfaces chunks the querying user is actually allowed to see. Access control isn't an app-layer filter bolted on as an afterthought; it's enforced twice, independently: once in the retrieval query itself, and again as a Postgres Row-Level Security backstop underneath it.

## Features

**Chat**
- Ask questions in natural language; answers are generated by Claude, grounded only in retrieved document excerpts (no hallucinated answers from outside the corpus)
- Streamed responses with Markdown + GitHub-flavored-Markdown rendering (tables, lists, etc.)
- Inline citation chips linking back to the source document and excerpt
- Per-user conversation history, fully private (no admin bypass — chat history is a personal log)
- Users with no accessible documents get a clear "ask an admin to share a document" state instead of a broken/empty chat

**Documents**
- Upload PDF, DOCX, TXT, or Markdown files (20MB cap)
- Async processing pipeline (extract → chunk → embed) via Inngest, with live status (`pending` → `processing` → `ready`/`failed`) and a surfaced error message on failure
- Per-document sharing: grant access to individual users or entire teams
- Admin-settable public/private visibility at upload time
- Document detail view with metadata and a chunk preview
- Owner-or-admin delete

**Teams**
- Admins create teams and manage membership
- Sharing a document with a team grants access to every current member — membership changes take effect immediately, with no per-chunk bookkeeping to update
- Normal users can view the team(s) they belong to; admins see and manage all teams
- Deleting a team cleans up its membership rows and every permission grant tied to it

**Admin**
- Role management: search users by email, promote/demote between `admin` and `user`
- Admin-only controls are enforced server-side (never just a hidden button) — non-admins get a 403 from the API itself, not just a UI redirect

**Account**
- Email/password auth (credentials + bcrypt, JWT sessions)
- Self-serve signup (always provisions a plain `user`, never `admin`, regardless of request body)
- Password change

## Architecture

| Layer | Choice |
|---|---|
| Framework | Next.js 16 (App Router), deployed to Vercel |
| Auth | Auth.js v5, Credentials provider, own `users`/`teams`/`roles` tables (not Supabase Auth) |
| Database | Postgres + pgvector on Supabase, via Drizzle ORM |
| Vector search | pgvector HNSW index (`vector_cosine_ops`), 1024-dim embeddings |
| Embeddings | Voyage AI (`voyage-4-lite`) |
| Generation | Anthropic Claude (`claude-haiku-4-5`), streamed |
| Async processing | Inngest (document extract/chunk/embed pipeline) |
| Data fetching | TanStack Query |
| Styling | Tailwind CSS v4 |

### The permission-filtered retrieval query

[`lib/retrieval/searchAccessibleChunks.ts`](lib/retrieval/searchAccessibleChunks.ts) is the **only** code path in the app allowed to read `document_chunks`. It does vector similarity search and permission filtering in one query — a document is visible if the requester is an admin, the owner, or it's been explicitly shared with them (directly or via a team), or the document is public. Centralizing this in one function means there's no second code path that could forget the check.

### Defense in depth: Row-Level Security

The same access logic is enforced a second time at the database level via Postgres RLS policies on `documents` and `document_chunks`, so a bug in the application query alone can't leak data. This runs through a dedicated, deliberately-restricted database role that (unlike the app's main connection) cannot bypass RLS, so the policies are actually load-bearing rather than silently skipped.

## Getting started

### Prerequisites

- Node.js
- A Supabase project (Postgres + pgvector + Storage)
- API keys: Anthropic, Voyage AI

### Environment variables

Create `.env.local` with:

```
DATABASE_URL=              # Supabase session pooler (migrations)
DATABASE_URL_POOLED=       # Supabase transaction pooler (app runtime)
DATABASE_URL_RLS=          # transaction pooler, connected as the restricted RLS-enforced role
SUPABASE_URL=
SUPABASE_SECRET_KEY=
AUTH_SECRET=                # `npx auth secret`
ANTHROPIC_API_KEY=
VOYAGE_API_KEY=
INNGEST_DEV=1                # local dev only
```

### Setup

```bash
npm install
npm run db:migrate
npm run db:seed         # seeds users/teams (admin/alice/bob, password: password123)
npm run db:seed:docs    # seeds a sample document (requires a manually-uploaded PDF, see script)
```

### Running locally

Two processes run side by side:

```bash
npm run dev
```
```bash
npx inngest-cli@latest dev   # document processing pipeline; dashboard at localhost:8288
```

The app runs at [http://localhost:3000](http://localhost:3000). Without `inngest-cli dev` running, document uploads will be accepted but never finish processing.

### Other scripts

```bash
npm run lint             # ESLint
npm run db:generate      # generate a new Drizzle migration from schema changes
npm run verify:sharing   # scripted check that team-sharing grants/revokes gate access correctly
```
